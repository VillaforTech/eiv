# Local model feasibility protocol addendum

Fixed before any test-model outputs on 12 October 2026, America/Guayaquil. This is stage 2 feasibility, not the primary empirical study. All outputs from development experiments remain in `results/smoke/` and `results/llm-dev*`; an interrupted development file without `finished_unix` is incomplete evidence, not a completed run.

The installed backend is Ollama 0.40.0, loopback only, Gemma 2 9B Q4_0 digest `ff02c3702f322b9e075e9568332d96c0a7028002f1a5a056e0a6784320a4db0b`. No models were downloaded, no external inference endpoint is supported and no inference charges were authorized. Temperature 0, seed 20261012, context 8192, at most three calls and **600 generated tokens per call** per arm. This tighter common ceiling replaces the earlier 1800-per-call feasibility allowance because development runs took tens of seconds per call. Actual consumption and failures are reported, not hidden behind the ceiling.

Development with free JSON formatting produced a local provider error (`prediction aborted, token repeat limit reached`). Schema-constrained output then produced invalid question partitions repeatedly, including references to candidates the model had not generated. The final adapter therefore uses schema-constrained outputs in every arm. EIV generates candidate policies and an empty question list; its deterministic policy constructs a complete candidate-choice partition from those candidates and asks only when their checked consequences disagree. This is a documented development-stage interface correction. The frozen initial prompt is supplemented with that output override; the exact provider request is retained for each call. It is not evidence that a model can generate good targeted questions.

Direct and conventional arms get one self-check if their first output is a final decision. Schema repair and clarification consume the same three-call cap. EIV uses the deterministic checker after valid generation. Conventional may ask one natural-language question; EIV may request the candidate-choice question. Both receive the same optimistic full-intent disclosure, or an insufficient-answer response. New factual assertions in that text are not inserted into the trusted fact map automatically: unknown conditions can therefore remain unresolved. No question quality or targeted information-gain advantage can be inferred.

Select two cases per each of the five test template groups before seeing test outputs: lexicographically first latent allow and deny cases where present, otherwise the first two cases. Exact IDs are in `benchmark/v2/llm-pilot-selection.json`. Ten paired cases and five synthetic clusters support only feasibility and failure inspection. The primary run has direct, conventional and EIV arms; the optional information-disclosure control is not included in this resource-bounded run. Consequently extra information is still a confound when comparing direct with either querying arm. EIV versus conventional shares answer access but uses a different representation.

Runtime/infrastructure/schema failures remain abstentions in the all-case denominator; describe their causes separately from semantic/formal/policy mistakes. Provider errors may omit token usage, so zero reported tokens in an error record means unavailable usage, not proof of zero computation. No selective retries, removals, prompt changes or policy optimization are permitted after this test begins. A new run after repairs must be separately versioned.

The run manifest saves data, selected IDs, model digest, decoder options, driver, prompt, schema and core hashes before execution. Raw messages, generated policies, explanations, questions, answers, usage and latency are saved incrementally. Analysis is replayable without the model. Regeneration requires the pinned weights/runtime and may still differ across hardware. Human label review is absent and is not simulated by another agent.
